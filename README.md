# WasteWise - daily bin collection for a municipal ward office

**IBM Datathon, 17-18 October 2026 · Challenge: Real-Time AI for Critical Decisions**

WasteWise tells the **Sanpada node ward office (Navi Mumbai Municipal Corporation, NMMC)** every day which
bins to collect, which truck goes where and in what order on the real streets, and shows afterwards
what the crews actually did. Overflowing bins cause public-health harm: rats, mosquitoes, dengue,
leptospirosis and blocked drains. Trucks have a fixed capacity and shift, so the order of collection matters.

> **Demonstration data.** No real fill-level data exists for Sanpada. The sensor history, collections and
> citizen complaints in the demo are **synthetic** (generated by `wastewise/synth.py`) and are labelled as
> such in the database (`synthetic = 1`) and on every screen. The streets, landmarks and landfill are
> real (OpenStreetMap). The forecaster is also tested on **real** smart-bin data from Mildura (Australia).

## Who uses it

| Role | Sees | Does |
|---|---|---|
| Control-room operator | Today's plan, Bins, What-if, Reports, Help | generates the plan, takes complaints, watches live alerts, re-plans during the shift |
| Ward supervisor | the same | approves plans, prints route sheets, enters returned paper sheets, edits the bin register |
| Administrator | the same + Settings | trucks, depot, users, API keys, AI engine, demonstration tools |
| Viewer | read-only | - |
| Collection crew (one account per truck) | **My route** only, on a phone | next stop, Google Maps, "how full", Collected / Could not reach / Bin missing, in English / मराठी / हिंदी |

## What it does

- **Bin register**: 50 bins at real Sanpada landmarks taken from today's OpenStreetMap extract, including
  stations, D-Mart Juinagar, hospitals, schools, parks, temples and housing societies. Each bin is
  kerb-snapped to a road where a truck may stop, never a flyover. Fleet: 3 trucks (12 000 / 12 000 /
  6 000 L), 06:00 shift of 4 h. The depot location and the Turbhe landfill gate are marked
  *confirm with NMMC*.
- **Road network**: a directed graph built from OSM, with one-way streets, roundabouts, a typical truck
  speed per road class and no stopping on flyovers. Dijkstra gives fastest-path time and distance matrices
  plus the street geometry for each route.
- **Prediction**
  - fill-rate forecaster: LightGBM gradient-boosted trees, scikit-learn HistGradientBoosting and their
    ensemble, with a chronological split, a locked test window, comparison with three baselines, and
    promotion only if more accurate;
  - sensor faults: rules plus scikit-learn IsolationForest. Faulty sensors are ignored in planning;
  - surges: the observed rise compared with the bin's normal pattern;
  - overflow risk: P(full) and expected overflow minutes as a function of the truck's arrival time.
- **Planning**: an own **Adaptive Large Neighbourhood Search** with five destroy and three repair
  operators, simulated annealing and local search.
  - Landfill trips are made whenever the next bin would not fit, and every route ends with a final unload.
  - Due bins are always served unless no truck has space or time; then an alert asks for an extra trip.
  - Capacity-sized vehicle areas (beats) carry a penalty for serving another truck's area.
  - The nearest-bin routine is computed as a baseline, and an **independent verifier** re-checks every plan.
- **What-if**: truck breakdown, a rush around a bin, or a spare truck, compared with the normal plan and
  adoptable as a draft.
- **Operations**
  - Today's plan: nothing is computed until *Generate plan*; Draft/Approved badges; a banner when new data
    arrived; alerts that each give a concrete action; *re-plan from now* during the shift only.
  - Map: truck-coloured lines and rings, fill-status centres, stop numbers.
  - Printable route sheets with landfill rows; the crew phone page; Progress (planned vs actual, late > 30 min,
    exceptions with actions, paper-sheet entry, CSV).
  - Complaints in English, Hindi, Marathi or mixed: "We understood: ... - confirm?". No bin is ever
    pre-selected, and if several places match the user is asked to choose.
  - Live alerts that refresh by themselves.
  - REST ingestion API protected by an API key.
- **Reports**: bin sizing, weekday x hour patterns, festival effect, 7-day outlook against fleet capacity,
  savings against the routine, and forecast accuracy.
- **Local IBM Granite** through a llama.cpp server on the same machine (built on s390x and tested with the
  big-endian Granite 4.0 H 350M *base* model, about 5.7 tokens/s; a base model does not follow
  instructions, so its texts are rejected by the check and the templates are shown): the pre-shift briefing, driver
  messages in English, Hindi and Marathi, and help locating the place in a complaint. **Every number, time
  and bin the model writes is checked against the plan.** If anything doesn't match, the checked template is
  shown instead and the reason is displayed.

## Architecture

```
 sensors / gateways ──REST (API key)──►  wastewise.api ─┐
 citizens (phone) ──► operator types complaint ─────────┤
 crews (phones) ─────► My route ────────────────────────┤      SQLite (WAL)  readings · events · complaints
                                                        ├────► plans · users · hash-chained audit · models
 OpenStreetMap (Overpass) ─► osm.py ─► roads.py (graph, matrices)
                                         │
  history ─► state.py / forecast.py (LightGBM · HistGB · ensemble; Snap ML on Telum) ─► risk.py
                                         │
                       planner.py ─► optimiser.py (ALNS) ─► verifier.py (independent) ─► plan JSON
                                         │                    baseline.py (nearest-bin routine)
                     Streamlit UI (app/) · llm.py ─► llama.cpp + IBM Granite (localhost only)
```

The core engine (`wastewise/`, apart from the models) needs only numpy and the standard library. The API
uses `http.server`, so no web framework has to be ported to s390x.

## Open-source AI packages used

scikit-learn (HistGradientBoosting, IsolationForest), LightGBM, XGBoost (built and tested on s390x; Snap ML
1.17.2 could not import its JSON format), llama.cpp with IBM Granite (open weights), plus numpy and pandas.
**IBM Snap ML** (proprietary licence, free to use) runs the boosted trees on the Telum accelerator.

## IBM LinuxONE (s390x)

Measured on the LinuxONE Community Cloud VM on 17 Oct 2026: machine type **9175 (IBM z17 family, Telum II)**,
big-endian, 3 vCPUs, Ubuntu 24.04, Python 3.12. Details and raw numbers are in
[docs/S390X_NOTES.md](docs/S390X_NOTES.md); run `scripts/capture_evidence.sh` on the VM to regenerate them.

- **No PyPI s390x wheels** for numpy, scipy, pandas, scikit-learn, pyarrow, LightGBM or XGBoost. The
  scientific stack comes from Ubuntu's s390x packages, and pyarrow 24.0.0 (needed by Streamlit) is built
  from the verified Apache source in about 7 min. LightGBM and XGBoost are built from source.
- **All 90 tests pass on s390x**; see [evidence/ibm-datathon1-20261017T094104Z](evidence/ibm-datathon1-20261017T094104Z)
  (captured by `scripts/capture_evidence.sh`, with SHA-256 checksums).
- Results came out identical on x86 and s390x: the synthetic generator produced the same 147 839 readings
  on both, and the forecaster's test errors match.
- Road network build (7 634 nodes): 0.32 s. A full plan: 8.5 s including 1 048 ALNS iterations (763 on the
  development laptop), verified independently. Forecaster training: 11 s.
- **Telum**:
  - The `nnpa` CPU flag is present and IBM zDNN 1.0.1 reports the accelerator as usable.
  - Snap ML had silently fallen back to the CPU until `libzdnn0` was installed.
  - **Measured result**: on this z/VM guest, Snap ML's accelerator path (`zdnn_tensors`) was *slower* than
    Snap ML on the CPU (`compress_trees`) for every LightGBM model size tried. For a planning batch
    (720 rows, all 3 threads) it took 1.45 ms against 0.78 ms (native LightGBM: 1.28 ms).
  - WasteWise therefore times both engines when the model loads, uses the faster one, and shows which in
    the header. *Settings > AI* can force the accelerator. We don't claim a Telum speed-up we didn't measure.

## Data sources

- **OpenStreetMap** via the Overpass API, downloaded on 17 Oct 2026 (OSM base 05:35 UTC).
  © OpenStreetMap contributors, ODbL 1.0.
- **Mildura RRC Smart Bin Fill Levels**, Mildura Rural City Council, data.gov.au, CC BY 3.0 AU,

- **Festival dates** (Ganeshotsav, Navratri, Diwali, ...) are approximate and should be checked against the
  official list.

## Security

- Passwords: PBKDF2-HMAC-SHA256 with a random salt and 600 000 iterations, lock-out after 5 failures.
- Stay signed in: after sign-in the browser keeps an HMAC-SHA256-signed session cookie (key in
  `secrets/session_key`), valid for one crew shift (12 h) or one office day (8 h), so a reload or a locked
  phone does not sign anyone out. Sign-out clears it and invalidates every earlier cookie of that account.
- Initial passwords are generated and written only to `secrets/initial_passwords.txt` (mode 600). They're
  never shown on the sign-in page.
- **Hash-chained, tamper-evident audit log** of every action, with an integrity check (*Settings*).
- API keys are stored only as SHA-256 hashes. The API is rate-limited and validates its input.
- No data goes to external services: usage statistics are off, the LLM is accepted only on localhost, and an
  offline map is available. With the default map, the viewer's browser loads OpenStreetMap tiles.
- Streamlit's developer toolbar and tracebacks are hidden. Role-based menus apply, and crews see only their
  own route.

## Run it

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt   # (s390x: bash scripts/vm_setup.sh)
.venv/bin/python -m wastewise.cli init          # OSM download, bins, fleet, accounts, API key, synthetic history
.venv/bin/python scripts/train_models.py        # forecaster + Mildura test + fault-detection evaluation
bash scripts/services.sh start                  # web app :8501 and REST API :8600 (127.0.0.1)
.venv/bin/python -m pytest -q tests             # tests
```

- **Container** (multi-arch, Podman on s390x): `podman build -t wastewise -f Containerfile .`
- **Granite**: `bash scripts/vm_setup_granite.sh /path/to/granite.gguf`. It builds llama.cpp, converts the
  model to big-endian if needed, and serves it on 127.0.0.1:8080.
- **Public link** (no firewall change): `bash scripts/vm_cloudflare_tunnel.sh` prints an `https://….trycloudflare.com` address.
- **Demo data**: `python -m wastewise.cli refresh-demo` (or *Settings > Refresh demo data to now*) moves the
  synthetic history up to the present. Manual records, settings, bins, trucks and users are kept.

## Limitations

- All Sanpada figures come from synthetic data, so they show that the method works, not the savings NMMC
  would actually see.
- The 180 days of history don't contain last year's Ganeshotsav, so the model can't learn that festival's
  effect.
- Bins without sensors are estimated far less accurately (MAE about 17 points): crews and supervisors
  estimate only to the nearest quarter or tenth.
- Gradual sensor drift is mostly missed (recall 12 %).
- The depot location and landfill gate are approximate. Truck speeds, service times and fuel factors are
  demonstration values to be set by the ward.
- The Telum accelerator didn't speed up these small tree ensembles on the shared z/VM guest (measured above).
- The available Granite model is a *base* model: on the VM its briefings fail the figure check, so the
  templates are used. An instruction-tuned Granite GGUF (converted to big-endian) is needed for fluent text.
- The public demo link is a Cloudflare *quick tunnel* (random `trycloudflare.com` address, no uptime
  guarantee); a named tunnel or an opened port is needed for permanent access.
