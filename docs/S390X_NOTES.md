# Running WasteWise on IBM LinuxONE (s390x)

Everything in this file was observed on the LinuxONE Community Cloud VM used for
the IBM Datathon (17 Oct 2026). Raw output is regenerated by
`scripts/capture_evidence.sh` into `evidence/`.

## The machine

| Item | Value (from `lscpu`, `/proc/cpuinfo`) |
|---|---|
| Architecture | s390x, **big-endian** |
| Machine type | **9175** = IBM z17 family (Telum II processor) |
| CPU flags | include `nnpa` (Neural Network Processing Assist = on-chip AI accelerator) |
| vCPUs / RAM | 3 / 7.8 GiB, under z/VM 7.3.0 |
| OS / Python | Ubuntu 24.04.4 LTS, kernel 6.8, Python 3.12.3 |
| zDNN | `libzdnn0` 1.0.1 (Ubuntu); `zdnn_is_nnpa_installed()` returns True |

## Where each library came from

PyPI has **no s390x wheels for CPython 3.12** for numpy, scipy, pandas,
scikit-learn, pyarrow, LightGBM, XGBoost or onnxruntime (checked with
`pip download --only-binary :all:`). Solutions used:

| Package | Version | Source on s390x |
|---|---|---|
| numpy, scipy, pandas, scikit-learn, pillow | 1.26.4, 1.11.4, 2.1.4, 1.4.1.post1, 10.2.0 | Ubuntu 24.04 s390x packages (`apt`), seen through a `--system-site-packages` venv and pinned with `constraints-s390x.txt` |
| pyarrow (needed by Streamlit) | 24.0.0 | Built from the Apache Arrow source release (SHA-512 verified) by `scripts/vm_build_pyarrow.sh`: Arrow C++ about 5 min, pyarrow about 2 min on 3 vCPUs |
| IBM Snap ML | 1.17.2 | Native `manylinux_2_28_s390x` wheel from PyPI |
| Streamlit, Plotly | 1.66.0, 7.1.0 | Pure-Python wheels |
| LightGBM, XGBoost | 4.7.0, 3.4.1 | Built from source with `pip install --no-binary` (gcc 13, about 10 min together) |

## Telum accelerator

Snap ML picks its accelerator build (`libsnapmllocal3_zdnn`) only if
`libzdnn` can be loaded. Without it, Snap ML prints *"Falling back to CPU-only
mode. IBM Snap ML will not leverage NNPA."* Installing `libzdnn0` fixed this
on this VM. `wastewise.platform_info` reports the machine type, the `nnpa`
flag and the zDNN check, and the UI header shows the result.

## Telum benchmark (measured on the VM, 17 Oct 2026)

`scripts/benchmark_telum.py` runs the forecaster's LightGBM trees (152 trees, 18
features) through IBM Snap ML 1.17.2 and writes `evidence/telum_<host>.json`.
`optimized_tree_format_` confirms `zdnn_tensors` really is used on the accelerator.

| Engine (3 threads) | 720 rows (one planning run) | 200 000 rows |
|---|---|---|
| native LightGBM, CPU | about 1.8 ms | 409 ms |
| Snap ML `compress_trees`, CPU | **0.93 ms** | **261 ms** |
| Snap ML `zdnn_tensors`, Telum accelerator | 3.9 ms | 1031 ms |

Size sweep (LightGBM, 100 000 rows, ms; timings vary by about 20 % between runs):
depth 4/100 trees: native 127, Snap CPU 25, Telum 359. Depth 6/500: 771 / 196 / 937.
Depth 8/500: 1013 / 274 / 1161. The latest run is in `evidence/telum_<host>.json`.

**Result: on this z/VM guest, with zDNN 1.0.1 from Ubuntu, the accelerator path was
slower than Snap ML on the CPU for every model size tried.** The gap narrows as
models get larger. Predictions agree with native LightGBM (mean absolute difference
below 0.001 %/h; the largest difference, 0.26, comes from float32 input rounding at
split thresholds). WasteWise therefore defaults to `auto`: it times both engines when
the model loads, uses the faster one, and shows which in the header. Settings > AI
can force the accelerator.

Re-measured in `evidence/ibm-datathon1-20261017T094104Z/telum_ibm-datathon1.json` with every engine
using all 3 threads (720 rows / 20 000 rows): native LightGBM 1.28 / 27.2 ms, Snap ML CPU 0.78 / 22.7 ms,
Snap ML Telum 1.45 / 39.9 ms. The CPU is still faster.

## Other s390x build notes

- **llama.cpp** (for IBM Granite) picks `-march=arch15` on a z17, which gcc 13 does not know;
  `scripts/vm_setup_granite.sh` builds for `z16` instead. The supplied
  `granite-4.0-h-350m-base-be.f16.gguf` is already big-endian and loads and generates (about 5.7 tokens/s).
- **cloudflared** has no s390x release binary; `scripts/vm_cloudflare_tunnel.sh` builds release 2026.10.1
  from source with the official Go 1.27.2 linux-s390x toolchain (checksum verified).

Snap ML 1.17.2 could not import XGBoost 3.4 JSON models ("no objective defined"),
so the forecaster exports its gradient-boosted trees from LightGBM.
